### 3. 🆕 [TRK-021](../REFERENCE-ERREURS.md#trk-021) — 19 des 23 commandes du catalogue sont déclarées SMS-only et partent en TCP

**Trouvé en tirant sur un fil du 12/08 :** deux commandes créées à 06:10:00, à **34 ms d'écart**,
par un utilisateur réel depuis la console — les premières commandes non-`fix_continuous` depuis le
**24/05**. Toutes deux `FAILED`, `channel = TCP`, `lastError = "ACK timeout: ACK timeout after
15000ms"`.

Or le catalogue dit, noir sur blanc, que ces deux commandes ne passent pas par ce canal
(`coban.catalog.ts:268-271`) :

```
// Templates dédiés au module SurveillanceMax. Envoyés via SMS car les
// commandes shock/sensitivity/noshock ne sont pas supportées sur le canal
// TCP descendant de la famille GPS103/403 — les ACK reviennent par SMS.
```

et le déclare dans la donnée : `availableVia: ['sms']`.

**Cause racine — la déclaration n'est lue par personne.** `availableVia` apparaît **une seule
fois** côté API (`tracker-commands.service.ts:396`) : pour être *exposée* au front. Elle n'est
lue nulle part côté web non plus (un champ de type, jamais consulté). Et `dispatch()` est explicite
sur son intention — *« Envoie une commande au tracker via TCP »* — sans jamais consulter le
template : il refuse si le boîtier est hors ligne, puis émet en TCP, quoi qu'il arrive.

**La routine qui manque est écrite dans le dépôt depuis l'origine** (`docs/07-sms-gateway.md:206`) :

```ts
if (online && template.availableVia.includes('tcp')) { … }
if (template.availableVia.includes('sms') && command.tracker.phoneNumber) { … }
```

**Portée : 19 templates sur 23.** Seuls 4 déclarent `tcp`. Les 19 autres sont proposés dans la
console et ne peuvent que retomber en `ACK timeout` — et le compteur le confirme sur toute
l'histoire : **6 `ACK timeout` en base, 6 sur 6 sur des templates SMS-only** (4 le 24/05,
2 le 12/08). Aucun essai n'a jamais abouti.

> Cette fiche **ne remplace pas** [TRK-012](../REFERENCE-ERREURS.md#trk-012), elle en est le
> jumeau à l'étage au-dessus. TRK-012 : le bon canal, la mauvaise enveloppe. TRK-021 : le mauvais
> canal, décidé alors que la donnée qui dit lequel choisir est déjà là. *Une déclaration que
> personne ne lit est pire qu'une déclaration absente : elle rassure.*

### 5. 🆕 [TRK-023](../REFERENCE-ERREURS.md#trk-023) — l'accusé de réception d'une coupure moteur devient une « Alarme inconnue » sans message

Première alerte de type `UNKNOWN` de toute l'histoire de la table, cette nuit à 00:04:26. Elle
porte le titre « Alarme inconnue », la sévérité `INFO`, et un **message vide**. La chaîne complète
est dans le journal de trames :

| Heure | Sens | Trame |
|---|---|---|
| 00:04:22.065 | — | commande moteur **CUT** manuelle (« depuis carte ») sur KSR370 |
| 00:04:22.075 | OUT | `**,imei:864035053277480,J;` |
| 00:04:26.079 | IN | `imei:864035053277480,jk,260813000425,…` |
| 00:04:26.091 | — | commande passée **`ACKNOWLEDGED`** — 4,0 s |
| 00:04:26.117 | — | **alerte « Alarme inconnue » créée pour l'exploitant** |

Le code `jk` n'est pas dans la table de décodage (`coban.parser.ts:27-61`, qui connaît `jt`, `kt`,
`it`, `dt`, `et`), donc `decodeAlarm` retombe sur `'unknown'` → le mapping produit une alerte
`UNKNOWN` → et `buildAlertMessage` retourne `null` pour ce type (`default: return null`).

**Deux défauts distincts, et il faut les traiter tous les deux :**

1. **Une réponse de commande n'est pas une alarme.** `jt` et `kt` sont mappés sur `acc_off`/`acc_on`
   → `null` → aucune alerte. `jk` échappe à ce filtre par sa seule absence du dictionnaire.
2. **Une alerte sans message.** Le repli `null` de `buildAlertMessage` produit une carte vide chez
   le client, alors que la trame brute est dans `payload`. Famille **brut** au sens du §7 : le
   message ne dit ni quoi, ni pourquoi, ni quelle conséquence.

⚠️ **Une occurrence, et la mesure le dit** : 2 lignes `wire_logs` pour **une seule** trame (journalisée
en `position` et en `ack`), sur un seul boîtier, en 3 jours — contre 202 `jt` et 209 `kt` sur
33-34 boîtiers. Le **mécanisme** est prouvé de bout en bout par le code et l'horodatage ; sa
**fréquence** ne l'est pas. À recompter avant d'en tirer un volume.

### 🔧 Rectification d'outillage — la table de rejets existe, elle n'a simplement pas les colonnes qu'on croyait

Le passage du 12/08 a écrit que `position_sampling_decisions` « n'existe pas » et n'a pas mesuré
TRK-015. **La table existe.** Ses colonnes sont `decision · state · reason · speedKmh · ignition ·
distanceM · receivedAt` — il n'y a **ni `createdAt`, ni `deviceTime`**. Les deux horodatages qui
servent à classer un rejet sont **dans le texte de `reason`** :

```
garde-fou ingestion (stale_devicetime) : deviceTime 2026-08-12T07:09:26.000Z vs dernier 2026-08-12T07:10:26.000Z
```

Et la table de jumelage est `positions."timestamp"`, pas `"deviceTime"`. Une requête qui utilise
les mauvais noms échoue avec « column does not exist » — un message qu'il est facile de lire comme
« la table a disparu ».

> *Une erreur de colonne et une table absente ne se distinguent pas dans le message d'erreur ; elles
> se distinguent en interrogeant `information_schema`.* Trois requêtes ont suffi. La mesure de
> TRK-015 reprend donc sa série, avec un trou d'un jour au 12/08.
